- Keep using the browser-to-node WebRTC Direct benchmark (`benchmark/webrtc-browser-direct-perf.mjs`) to validate whether any native-path wins generalize to a real browser path. The new best config is now the kept `mtu=1500` path with a `70%` bufferedAmount resume threshold. Instrumented browser errors on the old `75%` config reported `recentOutputs=[]`, and because the browser harness runs upload first that points specifically to the browser→node upload leg stalling before the first perf sample; the lower threshold appears to mitigate that stall. The shared-path compromise is still narrow and noisy, though: `69%`-`71%` can work, `71.5%` and `72%` re-break the `32 MiB` browser run, and tiny queue retunes around the new `70%` best (`sendBufferSize=3.125 MiB`, `recvBufferSize=2.25 MiB` or `1.75 MiB`, `MAX_BUFFERED_AMOUNT=1.75 MiB` or `2.25 MiB`) re-broke browser stability. The heavier browser region is now only partially mapped and clearly noisy: `64 MiB`, `72 MiB`, `73 MiB`, and even `84 MiB` can pass on some reruns, while `74 MiB`, `76 MiB`, `80 MiB`, `96 MiB`, and `128 MiB` have failed so far. A major new narrowing is that the current best can complete **upload-only** and **download-only** browser runs at `96 MiB`, download-only still succeeds with `reuseExistingConnection=false`, the full `96 MiB` upload+download workflow succeeds with a **fresh dialer per phase**, and it also succeeds on a shared dialer if the harness closes the original priming connection directly and waits for zero live connections before starting download. By contrast, removing the initial priming `dial()` reintroduces an early `recentOutputs=[]` upload/start stall, while `hangUp(target)` on the shared dialer either crashes node-side `WebRTCStream` sending with `errno=32` or still later stalls even after the connection table drains. A further diagnostic patch that simplified `connectionManager.closeConnections()` to close each connection directly made that previously bad `hangUp()+wait` workflow pass, and a narrower follow-up that still waited for the close event but sequenced it *after* `await connection.close()` passed too. That is the strongest current evidence that the bug lives in the connection-manager close path — specifically the current parallel `Promise.all([pEvent(connection, 'close'), connection.close()])` sequencing — rather than the shared WebRTC transport fast path itself. New node-only controls also help prune stale hypotheses: `benchmark/node-webrtc-shared-dialer-phase-repro.mjs` passes at `96 MiB` both with the priming connection left in place and with it closed before upload, while a simple 1 s browser wait between upload and download still fails. Recent browser connection snapshots also show at least two distinct post-upload states on the shared dialer: one where the priming connection already has a `timeline.close` and soon disappears, and another where it stays open indefinitely. So the next browser step should focus narrowly on browser-side connection lifecycle / teardown sequencing — especially `hangUp()` / `closeConnections()` versus direct connection close, and why the priming connection can remain open versus start closing after upload — not on one-way transfer tuning, generic libp2p perf sequencing, or more tiny threshold gardening. The older `mtu=1400 + MAX_BUFFERED_AMOUNT=3 MiB` fallback is still useful as a slower control up through `64 MiB`, but it is no longer a clearly more-robust large-transfer answer because it also fails at `84 MiB` and `96 MiB`, and it remains clearly slower overall. The next browser step should therefore focus on targeted diagnosis or retuning within the kept-`mtu=1500` / `70%`-ish pacing window, not on spending many more runs on the slower `mtu=1400` fallback unless a principled hypothesis appears.
