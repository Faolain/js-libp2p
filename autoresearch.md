# Autoresearch: Improve pure WebRTC browser streaming throughput

## Objective
Improve pure WebRTC data-path throughput as much as possible without relying on relay-assisted transport behavior or benchmark-specific cheating.

The user goal is browser streaming performance, but the most reliable in-tree benchmark here is a direct WebRTC streaming benchmark (`webrtc-direct`) using fixed-size transfers over reused connections, compared against an anchored TCP baseline measured on this machine. This isolates the shared stream/datachannel path, avoids relay flakiness, removes most TCP-side ratio noise, and avoids the timeout-driven instability seen with the original `benchmark/webrtc-perf.mjs` workload on this machine. Changes should target code shared with browsers where possible, not node-only shortcuts unless they are clearly scoped and justified.

## Metrics
- **Primary**: `webrtc_direct_tcp_ratio` (unitless, higher is better)
  - Defined as the mean of:
    - `webrtc-direct upload median / anchored tcp upload baseline`
    - `webrtc-direct download median / anchored tcp download baseline`
- **Secondary**:
  - `webrtc_direct_upload_mbps`
  - `webrtc_direct_download_mbps`
  - `tcp_upload_mbps`
  - `tcp_download_mbps`
  - `webrtc_direct_latency_ms`
  - benchmark wall time

## How to Run
`./autoresearch.sh`

This rebuilds `packages/transport-webrtc`, runs `benchmark/webrtc-direct-streaming-perf.mjs`, compares the result against `benchmark/webrtc-streaming-baseline.json`, and prints `METRIC name=value` lines.

## Files in Scope
- `packages/transport-webrtc/src/stream.ts` — stream framing / send path shared by WebRTC transports
- `packages/transport-webrtc/src/constants.ts` — message sizing and buffering limits
- `packages/transport-webrtc/src/muxer.ts` — data channel stream creation
- `packages/transport-webrtc/src/private-to-public/utils/get-rtcpeerconnection.ts` — node WebRTC direct peer connection setup
- `packages/transport-webrtc/src/webrtc/index.ts` — node-only WebRTC polyfill entrypoint
- `benchmark/webrtc-perf.mjs` — original benchmark harness/context
- `benchmark/webrtc-streaming-perf.mjs` — dual-transport fixed-size benchmark used to establish the anchored TCP baseline
- `benchmark/webrtc-direct-streaming-perf.mjs` — webrtc-direct-only benchmark used in the inner optimization loop
- `benchmark/webrtc-browser-client.ts` / `benchmark/webrtc-browser-direct-perf.mjs` / `benchmark/webrtc-browser-direct-perf-docker.sh` — browser-to-node direct benchmark harness for validating browser/shared-path behavior (host Playwright first, Docker fallback)
- `benchmark/webrtc-streaming-baseline.json` — anchored TCP baseline used for the ratio metric
- `autoresearch.sh` / `autoresearch.checks.sh` / `autoresearch.md`

## Off Limits
- No benchmark result fabrication
- No changing benchmark semantics to make the metric look better without real throughput gains
- No relay-dependent optimizations that hide pure WebRTC performance
- No changes outside WebRTC / benchmark support files unless clearly required

## Constraints
- Avoid overfitting to relay behavior; prefer `webrtc-direct`
- Prefer changes that help shared browser/node code paths
- Keep the benchmark workload representative
- Treat node-only MTU overrides as provisional until they survive the browser benchmark; local loopback can flatter packet sizes that are unsafe on real WebRTC paths where ~1200-byte payload budgeting matters for IPv6/path-MTU safety
- Maintain transport correctness; passing WebRTC tests is expected for kept results

## What's Been Tried
- Baseline from `benchmarking-results.md` on current branch: `webrtc-direct` is ~16.5x slower than TCP with 16 KiB messages and 2 MiB buffered amount.
- On this machine / Node 24, the original timeout-driven throughput harness could fail to capture `webrtc-direct` throughput samples even though direct perf transfers work. Switched autoresearch to a fixed-size, reused-connection streaming benchmark to keep experiments reliable while still measuring the pure data path.
- The first fixed-size 256 MiB benchmark still showed a lot of run-to-run variance, especially from the TCP side of the ratio. Increasing transfer size to 512 MiB reduced startup noise but did not remove enough TCP variance for small improvements.
- Current inner-loop metric anchors TCP to a session-local baseline from repeated 512 MiB runs and optimizes only the WebRTC direct side against that fixed reference.
- Even after anchoring TCP, the direct-only benchmark still shows meaningful residual noise. The workload has now been increased from 3 to 5 throughput iterations so future optimization decisions are driven more by sustained behavior and less by one-off run variance near the current frontier.
- Host-side Playwright/Chromium runs were previously blocked by missing system libraries, but the browser-to-node benchmark harness now works both directly on this host (`node benchmark/webrtc-browser-direct-perf.mjs`) and via the Docker fallback (`benchmark/webrtc-browser-direct-perf-docker.sh`).
- Quick host browser-to-node sanity checks with 64 MiB and 128 MiB transfers gave a mixed but suggestive MTU signal: forced `1500` consistently improved browser latency and often helped download throughput versus default/unset MTU in those runs, while browser upload stayed noisy and did not show a clear winner. A fresh 128 MiB rerun still showed nearly identical download with and without the MTU override, slightly better upload without it, and worse latency without it. More recent medium-workload checks on the newer `0.32.1` no-mux winner sharpened the trade-off further: the kept `mtu=1500` config passes lightweight browser smoke tests up to `20 MiB`, but still times out by `22 MiB` and above on the host browser path. Lowering only the explicit MTU to `1400` lets a `32 MiB` browser workload complete (roughly `141 Mb/s` upload, `237 Mb/s` download, `20 ms` latency) but drops the primary direct benchmark badly. Nearby compromise attempts at `mtu=1450` and `mtu=1420` still timed out in the browser run and also underperformed badly in the primary metric, and simple attempts to make the kept `mtu=1500` winner more browser-robust by shrinking `MAX_BUFFERED_AMOUNT` to `1.5 MiB` or shrinking `sendBufferSize` to `2.5 MiB` did not help. A broader `mtu=1400` queue-shape retry that kept the smaller `3 MiB` send / `2 MiB` recv buffers but raised `MAX_BUFFERED_AMOUNT` to `3 MiB` was more promising: it completed both `32 MiB` and `64 MiB` browser runs (roughly `165`→`198 Mb/s` upload, `264`→`302 Mb/s` download, `3`→`8 ms` latency) and improved the primary ratio over plain `mtu=1400` to `0.32530898248988743`, though it still trailed the kept `mtu=1500` best substantially. That more browser-tolerant `mtu=1400` + `MAX_BUFFERED_AMOUNT=3 MiB` regime also turns out to be narrow in its own right: raising the send buffer even slightly to `3.25 MiB`, pushing it to `4 MiB`, raising the wakeup threshold to `80%`, or shrinking the recv buffer to `1.5 MiB` all re-broke the `32 MiB` browser run. Treat the node-only `1500` win as plausible but still provisional until more representative browser coverage exists.
- A new raw native benchmark (`benchmark/node-datachannel-direct-perf.mjs`) now isolates node-datachannel/libdatachannel throughput without libp2p framing. Results continue to suggest the deeper stack is a major factor: default MTU is stable, lower MTUs are slower, and the `1400`-`1500` MTU region can crash/abort or time out in raw native mode even though the libp2p workload benefits from `1500` locally. A fresh raw rerun with the current libp2p-side queue shape (`6 MiB` send / `4 MiB` recv / `6 MiB` buffered limit / `82%` low watermark) still segfaulted at `mtu=1500`, timed out badly at `1472`, and remained stable at default/unset MTU.
- The actual node-side implementation in use is `node-datachannel@0.29.0`, which reports `libdatachannel 0.23.0` and statically links `libjuice` and `usrsctp` in the shipped prebuilt binary. Newer npm releases exist (`0.30.0`, `0.31.0`, `0.32.1`), but straight package swaps have not been promising so far: `0.30.0` built and benchmarked but regressed, `0.31.0` introduced hard TypeScript type incompatibilities in the current transport integration, and `0.32.1` reached runtime but failed almost immediately with `Sending failed, errno=32`.
- Now that `cmake` is available on this host, the default source-build path for `node-datachannel` is usable too. That deeper check did not unlock an easy win: a locally built `0.29.0`/`libdatachannel 0.23.0` stack stayed stable but still trailed the current best, a locally built `0.30.0` plus minimal `@ts-ignore` compatibility loosening still regressed, and a locally built `0.31.0`/`libdatachannel 0.24.0` still failed with the same early `Sending failed, errno=32` runtime error. So the remaining blocker does not look like a prebuilt-binary quirk on the default libjuice/OpenSSL path.
- Additional focused probing on the `libdatachannel 0.24.x` line first found a narrow, fair benchmarkable configuration, which helped localize the problem: removing forced `enableIceTcp`, removing the forced `mtu=1500`, disabling server-side `enableIceUdpMux`, and shrinking the queue shape to around `recvBufferSize=2 MiB`, `MAX_BUFFERED_AMOUNT=2 MiB`, and a `75%` resume threshold finally let the direct benchmark complete. Under that safer regime, `node-datachannel 0.31.0` reached `webrtc_direct_tcp_ratio=0.25918575216369977`, `0.32.0` reached `0.25583103872703394`, and `0.32.1` improved the 0.24 line to `0.2757192893376435`; a follow-up retune on `0.32.1` with `sendBufferSize=3 MiB` improved it slightly further to `0.27966127565036947`, while `4 MiB` slipped back and restoring `congestionControlModule=1` destabilized again. Source-building `0.32.1` did not help either, landing at `0.272613087729151`. Re-enabling either server-side `enableIceUdpMux` or explicit `enableIceTcp` on top of that safer 0.24 setup crashes/fails functionally again. Importantly, disabling server-side `enableIceUdpMux` on the older `0.29.0` aggressive best also crashes quickly, and pulling `0.29.0` all the way toward the same conservative no-mux/no-ICE-TCP/no-MTU regime times out too.
- The newer diagnostics then paid off: smaller native/polyfill repros showed that the 0.24.x aggressive repeated-send regression is not caused by explicit ICE TCP alone, but is strongly influenced by the interaction between server-side ICE UDP mux and queue depth. In the smaller repeated-send repro, disabling server-side ICE UDP mux alone makes `0.32.1` transfer `64 MiB` successfully under otherwise aggressive transport settings, and keeping mux enabled but shrinking the queue shape to `sendBufferSize=3 MiB`, `recvBufferSize=2 MiB`, `MAX_BUFFERED_AMOUNT=2 MiB`, and a `75%` low watermark also makes the repro stable. Applying that smaller queue shape back to the full benchmark while disabling server-side ICE UDP mux produced the first real breakthrough on the 0.24.x line: `node-datachannel 0.32.1` with `enableIceTcp=true`, `enableIceUdpMux=false`, `mtu=1500`, `congestionControlModule=1`, `sendBufferSize=3 MiB`, `recvBufferSize=2 MiB`, `MAX_BUFFERED_AMOUNT=2 MiB`, and a `75%` resume threshold reached `webrtc_direct_tcp_ratio=0.3428111466959902`, overtaking the old 0.29.0 best. A direct follow-up then showed explicit ICE TCP was no longer needed in that retuned regime: changing only `enableIceTcp` from `true` to `false` improved further to `webrtc_direct_tcp_ratio=0.3487076796437366` while checks still passed.
- Newer diagnostics have now localized that 0.24.x aggressive failure into smaller tracked repro surfaces. A minimal two-channel node-datachannel/polyfill repro (`benchmark/node-datachannel-polyfill-repeated-send-repro.mjs`) can open the negotiated handshake channel plus one application data channel on `0.32.1`, and a single `16 KiB` application send succeeds, so the newer stack is not simply unable to create one post-handshake channel. But once that same repro performs repeated application-channel sends under the aggressive queue shape (`6 MiB` send, `4 MiB` recv, `congestionControlModule=1`), it reproduces the regression even without libp2p framing: with server-side ICE UDP mux enabled it fails before delivering any app-channel bytes, around `16 MiB` sent with `mtu=1500`, around `8 MiB` sent with default/unset MTU, and still fails when `enableIceTcp=false`. Critically, disabling only server-side ICE UDP mux makes that same smaller repeated-send repro on `0.32.1` transfer the full `64 MiB` successfully. A paired stream-layer repro (`benchmark/node-datachannel-polyfill-stream-repro.mjs`) confirms the repo's `WebRTCStream` send path also reproduces on `0.32.1` and stays healthy on `0.29.0`, but the direct repeated-send repro shows the regression is not specific to protobuf framing or the broader libp2p upgrader/perf machinery. At this point, server-side ICE UDP mux looks like the clearest trigger in the newer aggressive regression surface.
- After moving the direct-only benchmark from 3 to 5 throughput iterations, the local optimum shifted somewhat. The older heavier-workload best on `0.29.0` used `mtu=1500`, `enableIceTcp=true`, `congestionControlModule=1`, `sendBufferSize=6 MiB`, `recvBufferSize=4 MiB`, and an `82%` bufferedAmount resume threshold, reaching `webrtc_direct_tcp_ratio=0.313742533089552`. The current best retained 5-iteration result now comes from `node-datachannel 0.32.1` with `enableIceTcp=false`, `enableIceUdpMux=false`, `mtu=1500`, `congestionControlModule=1`, `sendBufferSize=3 MiB`, `recvBufferSize=2 MiB`, `MAX_BUFFERED_AMOUNT=2 MiB`, and a `75%` bufferedAmount resume threshold, at `webrtc_direct_tcp_ratio=0.3487076796437366`. Frontier noise is still large enough that small differences need skepticism, and this newer native-heavy win now looks especially provisional for browser relevance: lightweight `16 MiB` browser sanity runs pass, the kept config also passes at `20 MiB`, but it still times out by `22 MiB` and above on the host browser path. Instrumenting the browser benchmark client to include recent perf outputs showed the kept `32 MiB` browser timeout fails with `recentOutputs=[]`, so the browser path is stalling before even the first intermediary perf sample is emitted rather than merely finishing too slowly; because the browser benchmark runs upload first, that specifically points to the browser→node upload leg of the kept config. Simple attempts to make the kept `mtu=1500` winner more browser-robust by shrinking `MAX_BUFFERED_AMOUNT` to `1.5 MiB` or shrinking `sendBufferSize` to `2.5 MiB` did not fix that browser timeout while also failing to improve the primary metric. The most promising shared-path fix so far is instead to make the send pacing slightly more conservative on the kept MTU path: lowering `bufferedAmountLowThreshold` from `75%` into roughly the `69%`-`71%` range makes the `32 MiB` host browser run complete while keeping the primary ratio close to the frontier (`0.3464` at `70%`, `0.3451` at `71%`, `0.3479` on one `69%` rerun, though follow-up reruns at `69%` slipped back to `0.3455`). Pushing back up to `71.5%` or `72%` re-breaks the browser run, so this browser-safe pacing window is real but narrow. It also does not fully solve robustness: a `70%` threshold can still time out on a `64 MiB` browser run, though a later rerun at the same setting completed `64 MiB` with about `212 Mb/s` upload and `300 Mb/s` download, so the new boundary is noisy rather than hard. Follow-up retunes around that `70%` compromise also showed how tight the safe region is: even tiny queue changes like `sendBufferSize=3.125 MiB`, `recvBufferSize=2.25 MiB`, or `MAX_BUFFERED_AMOUNT=1.75 MiB` re-broke the browser run while failing to beat the primary best. So the lower-threshold pacing fix is currently the strongest shared-path compromise, but it still has not matched either the pure primary best or the browser robustness of the slower `mtu=1400` fallback.
- Additional native-path probes after the MTU discovery have mostly failed to beat the current best: unset/default MTU, `1300`, `1472`, `1492`, single-sided `1500`, `enableIceTcp` on/off, `bindAddress=127.0.0.1`, `forceMediaTransport=true`, `disableAutoGathering=true`, `congestionControlModule` values `0`-`5`, delayed SACK retuning, npm package swaps to newer `node-datachannel` releases, and both ad-hoc and tracked repo-side fast RTCDataChannel wrapper experiments all improved some sub-metrics at times but still trailed the evolving best. Under the newer 5-iteration native best, removing `mtu=1500` now crashes partway through large transfers, reinforcing how tightly the current local win is tied to that override.
- Increasing `maxBufferedAmount` alone showed negligible gains in prior work, and raising it to 4 MiB on top of the new half-drain flow control caused transfer timeouts. Retesting 4 MiB, 5 MiB, and 6.5 MiB under the newer MTU-sensitive native tuning also trailed the 6 MiB best.
- Increasing `maxMessageSize` above 16 KiB failed with libdatachannel message-size limit errors in this environment. Reducing the shared chunk size below 16 KiB (e.g. `12 KiB`, `8 KiB`) also regressed materially under the current native tuning.
- Known good wins so far:
  - node SCTP buffer tuning helped materially; the current best retained 5-iteration setting is now `sendBufferSize=3 MiB`, `recvBufferSize=2 MiB`, `congestionControlModule=1`, `enableIceTcp=false`, `enableIceUdpMux=false`, and `mtu=1500` on `node-datachannel 0.32.1`, while the older `0.29.0` best used `6 MiB` send / `4 MiB` recv with mux enabled
  - raising `MAX_BUFFERED_AMOUNT` from the original 2 MiB to 6 MiB helped once combined with the later send/flow-control changes
  - resuming writes before full drain is important; with `MAX_BUFFERED_AMOUNT=6 MiB`, the best retained threshold under the current workload is `82%`
  - sending each framed WebRTC record with a single `RTCDataChannel.send(...)` call is now a confirmed win under the anchored direct-only benchmark as well as in the earlier PR experiments
  - removing the per-message receive-path log from `RTCDataChannel.onmessage` improved download throughput
  - the direct single-frame receive fast path and synchronous `RTCDataChannel.onmessage` callback both helped under earlier anchored direct-only runs and remain part of the current best stack
- Dead ends so far:
  - larger node SCTP buffers (`10 MiB`/`12 MiB`/`16 MiB` send, `5 MiB`/`8 MiB` recv) regressed or destabilized throughput
  - lower-level SCTP tuning exposed by node-datachannel/libdatachannel (`maxChunksOnQueue`, `initialCongestionWindow`, `delayedSackTime`) has so far regressed throughput or destabilized the connection, including a current-best retry with `delayedSackTime=10ms`
  - `MAX_BUFFERED_AMOUNT` at 1 MiB, 4 MiB, 5 MiB, 6.5 MiB, 7 MiB, or 8 MiB under the current send/flow-control regime trails 6 MiB or becomes unstable
  - receive thresholds at `50%`, `66%`, `70%`, `75%`, `80%`, `81%`, `83%`, and `85%` all trail the current `82%` best under the newer 5-iteration workload
  - reducing `MAX_MESSAGE_SIZE` below 16 KiB (`15 KiB`, `12 KiB`, `8 KiB`) regressed materially under the current native tuning
  - passing decoded protobuf payload `Uint8Array`s directly to `onData` instead of wrapping them in `Uint8ArrayList` regressed under the current best
  - resuming the write queue directly inside `onbufferedamountlow` stayed competitive but still trailed the current best
  - approximating `bufferedAmount` in the hot send loop instead of polling the real value each send destabilized the transfer and timed out
  - removing one microtask hop from the receive-side length-prefixed decoder startup did not help under the current best
  - a tracked node-only direct RTCDataChannel wrapper that bypasses the polyfill property-callback trampoline also trailed the current best
  - removing the per-message send-path trace call from `_sendMessage` also trailed the current best
  - removing broader hot-path logging earlier did not help under older configurations, but that result was configuration-sensitive
  - manual message-only frame encoding in JS regressed despite matching the existing wire format
- Prior branch work reportedly reached about `webrtc_direct_tcp_ratio ~= 0.073` on a different workload; continue re-evaluating improvements here without assuming node-only wins necessarily translate to browsers.
